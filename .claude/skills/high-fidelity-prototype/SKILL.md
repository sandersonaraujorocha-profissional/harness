# High-fidelity prototype (HTML + JS)

For any text written, follow the `communication-simplified` skill. Output text (screen content, user messages) stays in pt-BR. Identifiers (file names, `data-*` attributes, classes) stay as defined here.

Generates navigable screens paired with the diagram from the `screen-flow-diagram` skill.

## Fixed rules

1. **HTML and JS only.** No frameworks or build.
2. **One screen per `.html` file** in `prototipo/`.
3. **Modals in their own file** (`modal-<name>.html`), but **called from the parent screen**: the parent screen loads the modal HTML and shows it on top (see "Modals").
4. **No CSS written in the prototype**: no `<style>`, no `style=""` attribute, no `.css` created by this skill. Appearance comes from:
   - the CSS of the **visual identity manual** (skill `identity-visual-manual`), referenced by `<link rel="stylesheet" href="../identidade/tokens.css">` and `components.css`; or
   - if no manual exists yet, plain semantic HTML, and warn the user that visual fidelity depends on generating the manual.
   Use the manual's classes (e.g. `btn`, `btn-primary`, `card`, `modal`) and do not invent classes.
5. **Links paired with the diagram**: file name = node ID in Mermaid.

## Structure

```
prototipo/
  login.html
  dashboard.html
  modal-confirmar-saida.html
  _shared/
    app.js            # navigation + modal loading (only shared JS)
identidade/           # generated by skill identity-visual-manual (referenced, not created here)
docs/fluxos/*.md      # generated by screen-flow-diagram
```

## Markup conventions

- `<body data-screen="login">`: the value is the node ID in the diagram.
- Every navigation button/link has `data-id` equal to the button node ID in the diagram and `data-go` with the destination (screen ID):

```html
<button class="btn btn-primary" data-id="btn-entrar" data-go="dashboard">Entrar</button>
```

- A button that opens a modal uses `data-modal` instead of `data-go`:

```html
<button class="btn" data-id="btn-sair" data-modal="modal-confirmar-saida">Sair</button>
```

- Each screen has, in a comment at the top, the link to the documentation:

```html
<!-- Fluxo: docs/fluxos/cadastro.md | nó: login -->
```

## Modals

The modal file contains only the fragment (no `<html>`/`<body>`), with root `<div class="modal" data-screen="modal-...">`. The parent screen declares a mount point and `app.js` does the rest:

```html
<!-- inside the parent screen -->
<div id="modal-root"></div>
<script src="_shared/app.js"></script>
```

Modal buttons use the same `data-id`/`data-go`, and a button with `data-close` closes the modal without navigating.

## `_shared/app.js` (model)

Model: `templates/app.js`.

Note: `fetch` of local files requires an HTTP server (`npx serve prototipo`, `python -m http.server`). Tell the user when delivering.

## High fidelity without CSS

- Realistic content (texts, names, values), not lorem ipsum.
- Relevant states as separate screens or variations (`login-erro.html`), per the diagram.
- Minimal JS interactions: navigation, open/close modal, simple state toggling. No backend logic; use fixed data.
- Basic accessibility: `<label>`, `alt`, `role="dialog"` and `aria-modal="true"` on the modal.

## Pairing (mandatory)

- Every file here has a node in the flow `.md`, and vice versa. File name = node ID.
- Every button `data-id` exists as a button node in the diagram, and every `data-go`/`data-modal` points to an existing screen/modal drawn on the matching edge.
- When creating/changing/removing screens, update the diagram and the pairing table (skill `screen-flow-diagram`).
- Before finishing, list divergences: nodes without a file, files without a node, broken destinations, buttons without `data-id`. Fix or report.

## Workflow

1. Start from the flow `.md`; if it does not exist, create it first with `screen-flow-diagram`.
2. Generate `_shared/app.js` (once) and one HTML per screen/modal.
3. Run the pairing check and report the result.
